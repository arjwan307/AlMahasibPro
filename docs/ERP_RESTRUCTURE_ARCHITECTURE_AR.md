# خريطة إعادة بناء المحاسب برو — مستهدف معماري
**الحالة:** خطة تنظيم، وليست نقلًا منفذًا للملفات.
**المرجع الحاكم:** [ERP_MASTER_BLUEPRINT_AR.md](./ERP_MASTER_BLUEPRINT_AR.md)

## المبدأ
نظام واحد، قاعدة معاملات متماسكة، وحدات مجال أعمال مستقلة منطقيًا، واجهات متخصصة بحسب صلاحيات المستخدم. الحفاظ على الواجهات الحالية والبيانات الحقيقية وعدم تنفيذ إعادة كتابة شاملة دفعة واحدة.

## خريطة الوحدات المقترحة
| الوحدة | المسؤولية | حدود الربط |
|---|---|---|
| identity-tenancy | الشركات والفروع والمستخدمون والجلسات | جميع استعلامات البيانات تمر بعزل الشركة |
| authorization-audit | الصلاحيات والتفويضات والتاريخ المحاسبي | لا اعتماد دون تخويل، ولا تغيير بلا أثر |
| accounting-ledger | القيود اليومية والأستاذ العام والفترات | المصدر الوحيد للأثر المحاسبي |
| customer-ledger | لنا وله والفواتير والدفعات والتسويات | لا تسوية مشروطة قبل تحقق شروطها |
| wholesale-sales | عروض وفواتير الجملة والموافقات | السعر الفعلي محفوظ؛ لا خصم مخزني تلقائي |
| retail-pos | المفرد والفروع والشفتات والصناديق | التسوية المالية لا تكرر حركة الصندوق |
| warehouse-fulfillment | الكميات المحملة والرصيد والجرد | الخصم عند التحميل الفعلي |
| cash-collections | القاصة وعهد المحصلين وسندات القبض | قبض الزبون غير تسليم القاصة |
| fx-banking | العملات والتحويلات والبنوك | سعر الصرف الفعلي محفوظ ومدقق |
| imports-logistics | الموردون الخارجيون والحاويات والنقل | تفاصيل المورد سرية والحاوية مرجع تكلفة |
| payroll-assets | الرواتب والسلف والأصول والإهلاك | القيود تترحل للأستاذ العام |
| notifications | outbox واتساب وحالة التسليم | حدث القيد يولد الإشعار بلا تكرار |
| reporting | تقارير تشغيلية ومالية وإقفال | نفس صلاحيات المصدر |
| sync-offline | سجل عمليات محلي ومزامنة idempotent | لا يكرر الحركات عند إعادة المحاولة |

## العقود الحاكمة
1. كل حركة تحمل companyId وbranchId عند الاقتضاء وactorId وperformedBy وoperationId وtimestamp.
2. الاعتماد والتسجيل المحاسبي وحدث الإشعار ضمن معاملة متسقة أو outbox مضمون؛ لا تعتمد على نجاح واتساب لإثبات القبض.
3. القيد المعتمد immutable، وتصحيحه بحركة معاكسة أو تسوية مرتبطة.
4. فصل المستند التجاري، حركة المخزن، القيد المالي، وحيازة النقد؛ تربطها معرفات مرجعية لا تُدمج في سجل واحد.
5. لا يجوز أن يستنتج البرنامج من «الوظيفة» وجود حساب مستخدم.
6. تقارير التصدير وواجهات API تفحص التخويل من الخادم.
7. التشغيل دون إنترنت لا يسمح بتجاوز موافقات المدير؛ تحفظ العملية معلقة حتى الاعتماد وفق سياسة محددة.

## مراحل العمل الآمنة
1. جرد الشجرة البرمجية الحالية، قواعد البيانات، migrations، APIs، الواجهات، ونتائج CI؛ توثيق الموجود والناقص.
2. إضافة اختبارات ثوابت الأعمال الأساسية (التسوية المشروطة، عهدة المحصل، أسعار الصرف، التحميل الجزئي، العزل).
3. توحيد عقود العمليات والهوية والصلاحيات دون كسر API الحالي.
4. استخراج الخدمات من الملفات المتضخمة تدريجيًا عبر واجهات توافقية.
5. تفعيل إشعارات الزبائن من outbox موثوق بعد ضبط مزود واتساب والموافقة المطلوبة.
6. ترحيل بيانات تجريبي مع خطة rollback ونسخ احتياطي، ثم تحقق staging، ثم نشر تدريجي.
7. لا دمج إلى main قبل اجتياز CI واختبارات قواعد البيانات والأوف لاين.

## أشياء لا نفعلها
- لا إنشاء نظام مستقل للمشتريات المحلية؛ القيد من المصروفات أو المخزن حسب طبيعة الشراء.
- لا بناء سجل 66 مستقل؛ الأستاذ العام يكفي.
- لا منح الحسابات الخارجية صلاحية عامة لمجرد صفة محاسب.
- لا حذف واجهات أو بيانات حقيقية بسبب وجود عناصر تجريبية دون جرد.
- لا فرض سعر موحد أو خصم موحد على كل عملية.
- لا اعتبار الوثيقة إثباتًا بأن إعادة الهيكلة البرمجية اكتملت.

## معايير إغلاق المرحلة
تقرير مقارنة «الموجود/المطلوب»، اختبارات ناجحة، سجل migrations، خطة رجوع، وموافقة على الدمج.
